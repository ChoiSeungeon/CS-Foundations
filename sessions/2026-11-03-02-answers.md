## 01. RAM 기록과 SSD 파일 저장 구분 복습

질문 맥락: SSD 파일의 값 7을 RAM 작업용 복사본으로 읽고, 계산 결과 16을 RAM에 기록했지만 파일 쓰기·저장은 하지 않은 경우의 SSD 원본 값.

> 파일에 쓰거나 저장하는 동작을 하지 않았기 때문에 SSD 원본 파일의 값은 16으로 바꾸지 않고 아직 RAM에서만 16으로 기록되어 있습니다.

피드백 요약: 원본 파일은 7을 유지하고 RAM의 작업용 복사본만 16이라는 설명을 확인했다. 파일 읽기는 별도 작업용 복사본을 만드는 교육용 조건이다.

## 02. 읽기·연산·쓰기 흐름 재설명

질문 맥락: RAM 주소 120의 7과 주소 124의 9를 더해 RAM 주소 500에 기록할 때 CPU·레지스터·ALU·버스·RAM의 협력 순서.

> CPU에서 RAM에게 주소 120에 있는 7과 주소 124에 있는 9를 읽기로 요청하고 읽어오면 레지스터에 각각 저장합니다. 그리고 덧셈을 진행하고 그 값 또한 레지스터에 저장합니다. 그 이후 해당 결과를 RAM에 기록하기 위해 다시 RAM에게 주소 500애 결과 값 16을 저장을 요청하고 RAM은 요청을 받고 기록합니다.

피드백 요약: 읽기·레지스터 보관·결과 보관·CPU가 목적 주소를 지정한 쓰기 순서를 설명했다. 실제 덧셈의 주체는 ALU, 요청·데이터의 전달 통로는 버스라고 명시하면 더 정확하다는 짧은 수정안을 제공한다. 수정안은 학습자 원문에 합치지 않는다.

## 03. 같은 프로그램의 독립된 실행에 필요한 상태

질문 맥락: 계산기 프로그램 하나의 두 독립된 실행에서 서로 다른 계산을 유지하려면 구분할 정보.

> 각각 데이터를 저장하는 RAM의 위치와 레지스터 위치를 구분해서 관리해야합니다.

피드백 요약: 실행별 데이터와 레지스터 상태 구분이라는 방향을 확인했다. 물리적 레지스터 위치를 영구히 나누는 것보다, 실행별 레지스터 값을 저장·복원한다고 교정했다. 프로그램과 프로세스를 정의했다.

## 04. 한 코어에서 프로세스 A로 돌아갈 때의 상태 복원

질문 맥락: 실행 흐름이 하나씩인 프로세스 A와 B를 번갈아 실행한다. A의 R1=5였고 B 실행 중 같은 물리적 R1이 30이 된 뒤 A를 재개할 때의 처리.

> R1에는 5가 있어야합니다. 이를 위해서는 이전 프로세스 A의 실행 상태를 불러와야하고 B의 실행 상태를 저장해야합니다.

피드백 요약: A의 상태를 복원해야 함을 확인했다. 현재 B 상태 저장 후 A 상태 복원의 순서를 명시했다. 문맥 교환과 다음 명령 위치를 나타내는 PC를 소개했다.

## 05. 같은 프로세스의 스레드들이 PC 값을 공유하는지

응답 기준일: 2026-11-04(Asia/Seoul). 앞서 시작한 수업을 이어간 답변이며 실제 소요 시간은 추정하지 않는다.

질문 맥락: 메신저 프로세스에서 수신 스레드와 화면 갱신 스레드의 PC 값을 하나로 공유할지, 각 실행 흐름별로 보존할지.

> PC 값은 하나로 공유해야합니다.
> 스레드는 프로세스 안의 실행 흐름이고 PC값은 프로세스 단위로 저장하기 때문입니다.

피드백 요약: 스레드가 프로세스 안의 실행 흐름이라는 부분은 맞다. PC 값은 스레드별로 구분해야 한다는 점을 교정한다. 주소 공간 공유와 실행 위치 상태의 공유를 구분했다. 이후 06·14의 답변에서 다른 예시로 재확인했으며 첫 답변을 교정한 문장으로 바꾸지 않았다.

## 11. 지역 참조변수가 가리키는 공유 객체

질문 맥락: 프로세스의 공유 객체 box={value:0}. work()에서 지역 참조 ref=box로 같은 객체를 가리키고 ref.value를 1 증가시킨다. A 완료 후 B 실행의 출력.

> ref는 지역 변수이지만 공유 객체인 box의 참조를 복사하여 사용하였기 때문에 ref.value = ref.value + 1은 실제 공유 객체인 box의 value 값을 변경합니다. 그러므로 B가 출력하는 값은 2입니다.

피드백 요약: 지역 참조변수의 독립성과 대상 객체의 공유를 구분했다. 언어 중립 의사코드이며 Java 매개변수 전달 전체를 검증한 것으로 취급하지 않는다.
